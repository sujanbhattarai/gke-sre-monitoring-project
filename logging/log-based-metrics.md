# GKE Log-Based Metrics Engineering

## 1. Executive Summary

Implemented custom log-based metrics using Google Cloud
Logging to detect application-level HTTP errors across
NGINX workloads deployed on Google Kubernetes Engine.

The implementation converts application log events into
measurable operational signals for proactive monitoring,
automated alerting, and incident investigation.

## 4. HTTP 4xx Metric Configuration

Metric name: gke_application_http_4xx_count

Metric type: Counter

Units: 1

Logging filter:

    resource.type="k8s_container"
    resource.labels.cluster_name="cluster1"
    resource.labels.namespace_name="default"
    resource.labels.container_name="nginx"
    resource.labels.pod_name=~"^sre-demo-app-.*"
    textPayload=~"\" 4[0-9]{2} "

This metric captures HTTP client errors, including
400, 401, 403, 404, and 429 responses.

## 5. HTTP 5xx Metric Configuration

Metric name: gke_application_http_5xx_count

Metric type: Counter

Units: 1

Logging filter:

    resource.type="k8s_container"
    resource.labels.cluster_name="cluster1"
    resource.labels.namespace_name="default"
    resource.labels.container_name="nginx"
    resource.labels.pod_name=~"^sre-demo-app-.*"
    textPayload=~"\" 5[0-9]{2} "

This metric captures server-side errors, including
500, 502, 503, and 504 responses recorded by NGINX.

## 6. Metric Processing Architecture

NGINX Application Logs
    -> Google Cloud Logging
    -> HTTP Status Code Filtering
    -> Custom Log-Based Counter Metrics
    -> Cloud Monitoring
    -> Dashboards and Alert Policies

## 7. Metric Aggregation Strategy

| Configuration | Value |
|---|---|
| Resource Type | Kubernetes Container |
| Aggregation | Sum |
| Group By | None |
| Alignment Function | Rate for alert evaluation |
| Evaluation Window | 1 minute |
| Visualization | Line chart |

Summation combines error signals across application
replicas into a unified application-level time series.

Rate alignment converts counter measurements into
errors per second for threshold-based monitoring.

## 9. Alerting Strategy

| Metric | Demo Threshold | Target Severity |
|---|---|---|
| HTTP 4xx | 0.2 errors/sec | Warning |
| HTTP 5xx | 0.1 errors/sec | Error |

The thresholds were selected for controlled testing
and are not enterprise production recommendations.

## 10. Controlled Failure Validation

HTTP 404 errors were generated by requesting a
nonexistent application endpoint.

HTTP 500 errors were tested using a temporary NGINX
configuration on a separate port through Kubernetes
port forwarding.

This approach isolated the test endpoint from the
primary application endpoint and load balancer.

## 11. Recovery Validation

Following controlled failure testing:

- Temporary NGINX configuration was removed.
- NGINX configuration syntax was validated.
- NGINX was successfully reloaded.
- Both application pods remained Running.
- Zero container restarts were observed.
- The external application returned HTTP 200 OK.

## 12. Operational Limitations

- Log-based metrics depend on matching log entries.
- Metric ingestion and evaluation can introduce delays.
- Missing metric data does not always indicate zero errors.
- Application metrics do not capture all load balancer errors.
- Port-forwarded test requests bypass the load balancer.
- Final alert email delivery and closure require verification.

## 13. Production Recommendations

- Monitor HTTP error ratios relative to request volume.
- Implement SLO-based alerting and burn-rate policies.
- Establish thresholds using historical traffic patterns.
- Separate critical server errors from routine client errors.
- Evaluate metric cardinality and monitoring costs.
- Manage metric definitions through infrastructure as code.
- Maintain operational runbooks for alert investigation.

## 14. Engineering Outcome

Established custom application error monitoring using
Google Cloud Logging and Cloud Monitoring, providing
actionable visibility into application behavior and
supporting proactive site reliability engineering.
